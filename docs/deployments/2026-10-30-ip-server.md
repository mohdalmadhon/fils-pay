selects both and the correct environment file. API and PostgreSQL ports are
bound to loopback, settlement/reporting are internal. Firewall permits
22/80/443/8443. Existing infrastructure monitoring was retained.

The API retains its 0.5 CPU / 512-MiB limit and 320-MiB heap. Its measured
capacity on this hosted configuration has not yet been established; local

## Database, secrets and login

All 81 migration files, including 0084 and pg_trgm, applied to PostgreSQL 16.
The existing least-privilege service-role script was applied. An owner-format
custom database dump was saved before the first migration to
`/home/dilmune/backups/filspay-before-initial-migration.dump` (empty initial DB).
Persistent Docker volumes hold PostgreSQL and KYC data. Database-owner, service
role, internal API and webhook-encryption secrets were generated on the host,
stored with mode 0600 in `ops/.env`, and never put in Git or tool output.

The code uses its existing **acquirer simulator**, not a live payment provider.
The new server has its own random callback-signing secret in `ops/.env.docker`;
it is only for this simulator deployment. A real acquirer integration must use
the secret agreed with that provider. No live payment integration is claimed.

At the operator's explicit request, production stays enabled and
`OTP_DEV_EXPOSE=false`. Codes go to `/opt/filspay/private-otp/otp.jsonl` through
the API's private bind mount. The directory is 0700, file 0600, uid 1000;
logrotate keeps one daily compressed rotation. This file and the separate
credential directory are excluded from Git and Docker build contexts.
See [implementation and limitations](../fixes/operator-otp-file.md).

One initial super-admin account was created with a random password, rather
than installing default seeded accounts. Read its credentials over SSH:

```bash

sudo tail -n 10 /opt/filspay/private-otp/otp.jsonl
```

## Operations

```bash
sudo filspay-compose ps
sudo filspay-compose logs --tail 50 api reporting settlement
curl -k https://159.89.173.8/readyz
# Before future upgrades, take a new database backup (the first dump is empty):
umask 077
sudo docker exec filspay-postgres-1 pg_dump -U filspay -d filspay -Fc > ~/backups/filspay-before-upgrade.dump
```

Keep `ops/.env`, `ops/.env.docker`, the OTP/credential directories, PostgreSQL
and KYC volumes when updating source. Build new images before stopping services;
take a fresh backup before migrations. For a code-only rollback, select prior
image tags in the host override and recreate API/reporting/settlement with
`sudo filspay-compose up -d --no-build --no-deps api reporting settlement`.
Do not restore an old database over newly accepted payments as a code rollback.
Do not run the seed during routine upgrades: it is a deliberate database reset,
requiring explicit authorization and a fresh backup.
