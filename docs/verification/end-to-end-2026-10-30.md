# End-to-end verification: one payment, all the way through

| | |
|---|---|
| **Date** | 2026-10-30 (Asia/Bahrain) |
| **Code** | `main` at `b316fc2` (before the fixes) and `5d71309` (after) |
| **Flow checked** | Payment link → card payment → ledger → fees → settlement and payout → merchant webhooks → timeline, reports, reconciliation |
| **Re-run it** | `scripts/e2e/` (see [How to re-run](#how-to-re-run)) |

## What was asked

Confirm that:

1. the feature works from start to end, through the API
2. the money is right in the ledger, down to the fils
3. fees and payouts come out right
4. the shop gets the right webhook
5. it shows up right in the timeline, the reports and reconciliation
6. the app is live on Dilmun Cloud, our hosting provider

## How it was checked

Real services against a real Postgres 16. Nothing was mocked.

- **Database:** a new, empty database, built with `npm run migrate` and then `npm run seed`. The seed's own assertions passed.
- **API:** `apps/api` on its own port, with the webhook dispatcher polling every second.
- **The shop:** a small HTTP receiver that records every webhook delivery, headers and raw body.
- **Settlement:** `apps/settlement` built from source and run as `settlement run-batch --date=<today> --merchant=<Alpha Retail>`.
- **Reporting:** `apps/reporting` run as `catch-up`.

The merchant was Alpha Retail Co (seed). Its `merchants.mdr_bps` is 250, but
its fee schedule says 225 bps from 2026-08-01, so 225 is the rate that
applies. The steps, all through the HTTP API except where noted:

1. Merchant signs in (password, then OTP).
2. Merchant registers a webhook endpoint pointing at the receiver.
3. Merchant creates a payment link for **47.333 BHD** (47,333 fils). The amount is chosen so the fee rounds and the scheme file truncates.
4. The customer reads the link and pays it with no session (`Idempotency-Key` set). The customer then tries to pay again.
5. Read back the transaction and its timeline.
6. Check `ledger_entries` directly in SQL.
7. Run settlement for the day. Check the batch, the scheme file line, the payout legs and the disbursement.
8. Check webhook deliveries and verify each signature with the endpoint's secret (`HMAC-SHA256` over `t.body`).
9. Run the reporting worker. Read volumes, top links, payout trends, the batch's transactions and the reconciliation report.
10. A second payment of **12.345 BHD**, left unsettled, to check how reconciliation treats pending money.

## Results before the fixes (`b316fc2`)

| # | Check | Result |
|---|---|---|
| 1 | Works start to end through the API | ✅ The flow passes. ❌ But a fresh `npm run migrate` stopped at `0054_views.sql` (`settlement_batch_events` does not exist), and `0055` failed next (`chart_of_accounts.code` does not exist). 0055–0077 never applied. Existing dev databases worked only because 0054/0055 had been skipped by hand. |
| 2 | Ledger right to the fils | ❌ The capture group balanced (47,333 gross; 1,065 fee = 47,333 × 2.25% = 1,064.99, rounded half-to-even). No group in the ledger was unbalanced. But the scheme file line was 47,330, and the 3-fils residue that ADR 0002 says CloseBatch journals was posted nowhere. |
| 3 | Fees and payouts | ✅ Batch: gross 47,333, fee 1,065, net 46,268. Payout legs balanced, one disbursement, and merchant payable for the payment ended at exactly 0. |
| 4 | Webhooks | ✅ `transaction.captured` (fee 1,065) and `settlement.paid` (net 46,268). Both signatures valid, both delivered on the first attempt. |
| 5 | Timeline, reports, reconciliation | ✅ Timeline: `authorized` then `captured` with the fee. ✅ Volumes, top links, payout trends and batch transactions all show the payment. ❌ Reconciliation: "not explained", gap −46,268. With the second payment pending it was −46,237 (the payout counted as a gap, plus pending priced at 250 bps instead of 225). |
| 6 | Live on Dilmun Cloud | ❓ Not checkable from here. There is no access to Dilmun Cloud and no deployment configuration for it in the repo (only `ops/docker-compose.yml`). |

A note on the reports: the day's volume also included a 150.031 BHD
`transaction.captured` outbox event from the seed, whose transaction does not
exist. That is seed data, not a reporting error.
